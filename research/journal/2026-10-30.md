## 3. 실제 generate logits 캡처 기능: 이미 존재함

`experiments/diagnose_rate027_baseline.py:57`의 **RecordingModel.generate**가 production `_binary_choice_completion` 호출을 위임하면서 `return_dict_in_generate=True`, `output_scores=True`, `output_logits=True`를 추가한다. 원래 prefix_allowed_tokens_fn의 허용 ID 호출을 기록하고 `.sequences`를 helper에 반환한다. raw logits가 없으면 processed scores로 대체하지 않고 실패한다.

같은 파일의 `candidate_layout`, `allowed_at`, `run`, `summarize_repeats`는 공통 접두/첫 분기, 각 실제 생성 단계의 prefix/허용 ID, raw logits, raw full-vocab·allowed log-softmax, processed_generation_score, selected_token_id, 생성 EOS 포함 token IDs 및 환경 정보를 기록한다. `run`은 token/logit/score 길이와 실제 trie 허용 집합을 대조한다. self_test 정의도 있으나 이번에 실행하지 않았다.

**재사용 판단:** 캡처 wrapper와 정렬·trie 대조·환경 기록 방식은 재사용 가능하다. 현재 실행기는 `hagendorff_crt_rate_027` 고정, 무개입, SAE 미로딩, ≥5 completions를 전제로 한다. 이 실행기를 그대로 실행하면 요청한 Fresh v2/30908 검증이 되지 않는다. 저장소 results에서 rate027 진단 Artifact는 발견되지 않았다. 따라서 기능의 코드 존재는 확인했지만 실제 GPU 성공 실행은 확인하지 못했다.

별도 캡처 엔진을 새로 만드는 제안은 불필요하다. 필요한 것은 이 방식의 Fresh v2 조건 연결·개입 hook 연결·관측 가능 여부 및 감사 비교 출력의 최소 확장이다. 원래 모듈의 무개입 진단 목적을 유지하도록 별도 opt-in 진입점에서 helper/RecordingModel을 재사용하는 방안을 우선 검토한다. 이번에는 구현하지 않았다.

주의: 기존 진단의 `correct_minus_lure_raw_logit_margin`은 이번 감사의 lure−correct와 **부호가 반대**다. 기존 `first_branch=branches[0]`는 허용 토큰이 둘 이상인 최초 관측 단계이며, 후보 EOS 분기와 다중 EOS까지 포함하면 후보의 첫 의미 분기와 항상 동일하지 않을 수 있다. 명시적 위치·prefix 검사 없이 그대로 사용하면 안 된다.

### 확인된 사실과 가능한 원인

- **공통 사실:** 대상 7문항 모두 B 후보는 `[220, 숫자, 숫자, 2756]`, 공통 prefix `[220]`(선행 공백), 첫 분기 위치 2(1-based)다. Correct/Lure 길이는 모두 4로 같고 prefix collision이 없다. 두 후보 뒤에는 days 토큰이 붙는다. 단순 후보 길이 차이가 이 19슬롯의 직접 설명은 아니다. B trajectory에서 Tie인 두 첫 분기 token_logprob는 저장 정밀도상 정확히 같았다. 실제 생성의 raw logits가 같았다는 관측은 아니다.
- **T-C:** +7 growth_008(2슬롯), 009(3슬롯)는 teacher-forced Tie이나 실제 Correct. Lure branch ID 16이 Correct ID 18보다 작다. 실제 처리 후 점수도 동률이고 full-vocab argmax가 낮은 ID를 고르는 환경이라면 Lure가 예상되므로, 단순 낮은 token ID tie-break만으로 관찰된 Correct를 설명할 수 없다. 실제 생성은 비Tie였거나, 처리된 score·수치 실행 조건이 달랐을 가능성이 있으나 미검증이다.
- **T-L:** +7 growth_012/013(각 3슬롯), +8 growth_007/026(각 3슬롯)는 Tie·Lure label이다. 각 Lure branch ID가 Correct보다 작아, 실제 처리 후 점수도 동률일 때 낮은 token ID tie-break와 양립한다. 그러나 실제 생성 logits/argmax 구현을 관측하지 않았으므로 원인 확정은 아니다. +8 문자열 원본도 미확인이다.

## 5. 다음 실제 생성 추적 설계 (미구현·미실행)

기존 RecordingModel의 캡처 기능을 재사용하고 다음 연결만 추가하는 방향이다. 새 generate loop나 teacher-forced 실험을 재구현하지 않는다.

1. **입력·개입:** 기존 inventory의 case/slot, Base 모델, 원래 instruction/raw prompt/선행 공백 후보, Layer 5/30908/all, coefficient 0/+7/+8을 고정한다. `steer_generation_labels`와 같은 hook 등록/제거 방식 및 production `_binary_choice_completion`을 그대로 사용한다. baseline 무hook와 coefficient 0 hook 동등성은 CPU 검증 대상으로 명시한다.
2. **실제 생성 관측:** RecordingModel로 기존 generate를 감싸 `output.logits`(후보 제한 전 raw), `output.scores`(제약 및 모든 processor 적용 후), `.sequences`와 실제 허용 ID를 수집한다. 처리 후 score를 원본 logit으로 대체·명명하지 않는다. 원본이 없으면 unsupported로 실패하며 우회 추정하지 않는다. 최종 선택은 scores argmax 추정값이 아닌 실제 sequence의 token ID로 기록한다.
3. **관측 조건:** expected first-divergence index는 후보 ID의 common prefix 길이 k(0-based). 실제 step k가 존재하고, 실제 generated[:k]가 정확히 후보 공통 prefix이며, 해당 Correct/Lure next IDs가 모두 허용될 때만 observed=true. raw margin은 **같은 실제 forward의 `raw[lure]−raw[correct]`**로 계산한다. 분기 전 EOS/중단/예외/경로 이탈이면 margin=null·미관측 사유를 저장한다. teacher forcing 또는 도달 뒤 재구성으로 채우지 않는다.
4. **EOS/접두 관계:** 여러 EOS ID, 두 후보 중 하나가 다른 후보의 접두인 경우는 EOS vs 계속 token 경쟁으로 명시한다. 여러 EOS 중 하나를 임의 후보 대표로 선정하지 않는다. 첫 후보 분기와 단순 EOS ID 선택 단계를 구분한다. 생성 token IDs에는 EOS를 보존하고 응답 문자열·종료 여부·종료 사유·끝난 step을 별도 기록한다. 문자열 strip으로 EOS 관측을 대체하지 않는다.
5. **세 경로 비교:** 기존 B teacher-forced First/Full Margin은 원본 CSV에서 read-only join. 새 실제 raw first margin, processed score 차이, 허용 ID·실제 선택 ID·완성 응답 label을 별도 열에 기록한다. 과거 label, 이번 instrumented label 및 무계측 production label을 구분하고 재현 여부를 표시한다. 후보 제한으로 강제된 공통 prefix에서 raw top token이 후보 밖일 수도 있음을 기록한다.
6. **출력·관측 단위:** 최소 필드: case_id, split_seed/slot 출처, coefficient, input/hash, model/tokenizer/SAE revision, dtype/device/cache/generation_config, k·observed·reason, actual prefix, allowed IDs, raw C/L logits·margin, processed C/L scores·선택 ID, generated IDs/EOS, answer/label, 기존 B Margin/과거 actual label. Teacher-forced margin은 case×계수 1개를 여러 split slot에 연결한 값이며 새 측정도 고유 조건별 실행과 슬롯 join을 구분한다.

## 9. 5-B 코드 리뷰 후 최소 보완 (2026-10-30 후속 기록)

### 9.1 완료 상태와 예외 처리

`inspect_capture`는 `eos_observed`/`eos_terminated`, `complete_candidate`/`candidate_label`, `helper_accepts_tokens`, `behavioral_response_valid`, 기존 `observed`(분기 관측)를 분리한다. 후보 대조는 기존 helper처럼 **끝의 EOS만 제거**하여 수행한다.

기존 binary helper는 EOS 없이 후보 ID가 완성되어도 응답을 반환한다. 이 반환 규칙은 유지하고 `capture_case`의 `answer` 및 `helper_returned_response`에 보존한다. 진단에서 정상 종료 응답으로 인정하는 `behavioral_response_valid`는 후보 완성·EOS 종료·유효한 제약 경로를 요구한다. EOS 없는 후보 완성은 `candidate_complete_without_eos`, `candidate_label`은 유지하지만 `new_generation_label=null`이며 과거 label 일치율에 임의로 포함하지 않는다. 분기에 이미 도달했다면 이 경우에도 `observed=true`일 수 있다. 부분 답안 및 조기 EOS도 후보 완성·분기 관측과 별도로 기록한다. 이 엄격한 완료 판정은 새로운 진단의 기준이며 과거 Behavioral 채점 규칙을 소급 변경하지 않는다.

`capture_case`의 RuntimeError 포괄 변환을 제거했다. 신규 `expected_incomplete_error`는 실제 반환된 캡처가 있고, traceback의 최종 프레임이 production helper이며, case ID와 실제 반환 token IDs로 만든 최종 미완성 오류 문구가 정확히 일치하는 경우에만 진단용 미완성 상태로 변환한다. 모델/kernel·raw 미지원·기타 예상하지 못한 RuntimeError는 그대로 발생시킨다. Hook은 정상/예외 모두 finally로 제거한다. 향후 helper 오류 형식 변경 시 조용히 추정하지 않고 실패한다.

### 9.2 향후 실제 GPU 계측 동등성 검증 준비

신규 `SequenceRecordingModel`은 비계측 경로의 `generate` 인자와 반환값을 그대로 전달하고, 반환 sequence만 읽는다. logits/scores/return flags 또는 prefix callback을 추가·변경하지 않는다. `compare_uninstrumented`는 같은 모델·문항·계수에서 기존 helper를 한 번 더 호출하며 동일한 Hook factory·등록/제거 방식을 사용한다. EOS를 포함한 generated token IDs와 최종 helper 응답의 동일성을 각각 저장한다. 두 비교가 모두 맞아야 `equivalent=true`다. 동등성 검사의 예외는 그대로 발생시킨다. 순서는 계측 → 비계측으로 기록하며, 이는 해당 두 호출의 관측 비교이지 모든 실행에서 동일함의 보증이 아니다.

`run_model`/CLI에 opt-in `--check-equivalence`를 추가했다. 기본 실행은 기존 21회이며 옵션이 없으면 `equivalence_check.status=not_run`이다. 옵션을 켜면 **21개 고유 조건마다 두 경로, 총 42회 generate 호출**이 예상된다. 추가 21회는 같은 조건의 경로 검증이며 신규 독립 조건 또는 seed별 반복 측정으로 세지 않는다. 이번에는 두 GPU 경로 모두 실행하지 않았다.

Python 호출 순서상 run_model 반환 이후 직렬화 단계이며, JSON 파일 open 이전이다. 실제 `actual_first_divergence.json`은 남아 있지 않으므로 해당 실행의 raw logit/Equivalence 수치를 복원하거나 관측 완료 결과로 기록하지 않는다.

문제의 데이터 경로는 다음과 같다.

`run_model().environment = diagnose_rate027_baseline.environment(...)`

→ `environment.model_configs.model.dtype` / `.model.torch_dtype`

→ `environment.model_configs.text.dtype` / `.text.torch_dtype`

공유 environment 함수가 model.config 및 model.config.text_config의 이 속성을 `getattr`로 그대로 dict에 복사했다. 이 값이 문자열이 아닌 torch.dtype이면 엄격한 JSON serializer가 거부한다. 파라미터 dtype·SAE dtype 등은 이미 문자열 변환을 하고 있었으나 이 config 속성 네 곳은 빠져 있었다. **로그는 타입만 표시하고 개별 키를 표시하지 않으므로 네 경로 중 최초 예외 필드 하나나 실제 dtype 값을 A100 산출물만으로 확정하지는 않는다.** 같은 구조의 CPU Mock으로 원인·수정을 검증했다.

### 13.2 최소 수정 및 보존한 동작

`experiments/diagnose_rate027_baseline.py:environment`의 config 수집 직후, dtype/torch_dtype 필드에 한해 `isinstance(value, torch.dtype)`이면 `str(value)`를 저장하는 5줄을 추가했다. model/text 양쪽에 적용하며 모델 config 자체는 수정하지 않는다. 기존 문자열 및 None은 보존한다. 진단 스크립트는 이 공유 함수를 사용하므로 `experiments/trace_fresh_v2_first_divergence.py`를 별도 수정하거나 변환 로직을 중복 추가할 필요가 없었다.

### 18.6 해석·다음 단계

이 단일 사례에서 계수 증가에 따라 실제 첫 분기 Margin이 Correct 우위에서 동률로 이동하고 +8 응답이 Lure로 바뀌었다. Full/TF/Actual 지표가 다른 현상을 실제 동일 문항에서 확인했으나, Feature가 일반적 직관 오류나 추론 능력을 담당한다는 주장은 입증되지 않았다. N=1 사례·선택된 예외·서로 다른 실행 시점·정확한 revision 미기록이라는 한계를 유지한다.

다음은 우선 추가 GPU 없이 TF와 생성의 cache/연산 길이·정밀도·프롬프트 ID 정합성을 더 정밀하게 비교하고, 향후 필요 시 정확한 revision/환경 고정 및 사전 정의된 대조 문항·Feature/방향 대조를 설계하는 것이다. FP32 민감도나 독립 사례 확장은 별도 설계·사용자 GPU 승인 후에만 검토한다. 이번에 재실험·새 Colab 세션·모델 다운로드는 하지 않았다.

사용자가 요청한 검증 기록·분석 코드·테스트·신규 결과만 main에 Commit/Push하며, 실제 SHA와 Push 성공 여부는 완료 응답에 기록한다. 기존 Artifact와 이전 Journal은 보존한다.
