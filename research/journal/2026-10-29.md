### 7.2 Margin 정의 및 계수별 비교

`Full Margin = log P(Lure answer | prompt) − log P(Correct answer | prompt)`

- 양수: 두 후보 중 Lure의 상대적 Likelihood가 큼.
- 음수: Correct의 상대적 Likelihood가 큼.
- `Δ Margin(c) = Margin(c) − Margin(0)` (동일 문항·프로토콜 기준).
- Teacher-forced 전체 후보 토큰 Log-Likelihood 합계이며, constrained greedy 실제 생성 결과나 정답률이 아님. EOS 미포함.

| 지표 | Protocol A (diagnostic_compatible) | Protocol B (behavior_compatible) |
|---|---:|---:|
| Baseline 평균 Margin | +0.156973 | −0.439242 |
| +7 평균 Margin | +0.642397 | +0.902768 |
| +8 평균 Margin | +0.629336 | +0.583226 |
| +7 평균 Δ Margin | +0.485425 | +1.342010 |
| +8 평균 Δ Margin | +0.472364 | +1.022468 |
| Baseline Correct 선호 문항 | 18/33 | 20/33 |
| +7 Correct 선호 문항 | 13/33 | 8/33 |
| +8 Correct 선호 문항 | 13/33 | 12/33 |

Protocol B 단독 평균 Correct/Lure log-likelihood:

| 후보 | Baseline | +7 | +8 |
|---|---:|---:|---:|

**관찰:** 양의 개입에서 두 프로토콜 모두 평균 Margin이 Lure 쪽으로 이동했다. 특히 B의 +7 Δ Margin은 A보다 +0.856586, +8은 +0.550104 크다. 그러나 개입 후 Correct와 Lure의 절대 로그우도는 모두 크게 낮아져, 상대 Margin 증가를 모델의 전반적 생성 성능 향상으로 해석할 수 없다.

### 7.4 해석의 한계 및 다음 작업

1. Paired Bootstrap 95% 신뢰구간과 문항 단위 통계 검증은 **아직 수행하지 않음**. A/B 평균 차이가 통계적으로 안정적인지 결론 내리지 않는다.
2. `token_trajectory.csv`를 활용한 첫 분기 토큰 vs 전체 답변 Margin의 기여 분석은 **대기 중**.
3. 실제 Behavioral 생성/Correct-Lure 분류 결과와 Likelihood의 문항별 일치성 검증은 **대기 중**.

5. 후속 단계: 재현 가능한 A/B 분석 스크립트 작성 → paired bootstrap → 토큰 수준 분석 → Behavioral 교차 검증 → 논문용 표/그림.

> 1~6절은 당일 초기 계획 당시의 상태를 보존한 기록이며, 이후 수행된 실제 실행 및 결과는 7~8절에 추가했다.

### 9.2 Protocol A/B 정의

- **Protocol A — Diagnostic-Compatible Full-Answer Likelihood:** 기존 진단 방식에 맞춘 입력 및 후보 토큰화 조건에서 Correct/Lure의 **전체 답변** teacher-forced 로그확률을 비교하는 실험. 입력 프로토콜 식별자 `diagnostic_compatible`. 2026-10-23 실행.
- **Protocol B — Behavior-Compatible Full-Answer Likelihood:** 기존 Behavioral 생성 평가와 더 가깝게 맞춘 입력 조건에서 동일한 Correct/Lure 후보의 전체 답변 로그확률을 다시 측정하는 실험. 입력 프로토콜 식별자 `behavior_compatible`. 2026-10-29 실행.
- **공통점:** Qwen3.5-2B 계열, Layer 5 SAE Feature 30908, `token_position=all`, 동일 33개 Growth 문항과 개입 계수 0/+7/+8, EOS 미포함. 문항/계수 조합 99개씩.
- **차이 및 주의:** 두 프로토콜은 입력 포맷과 후보 토큰화가 달라질 수 있으며, 결과 차이를 **프롬프트 하나의 효과**로 분리해 주장할 수 없다. Protocol B가 Behavioral 생성과 완전히 동등한 실행 조건임을 입증한 것도 아니다.
- **Full Margin 정의:** `full_margin = log P(Lure candidate | prompt) − log P(Correct candidate | prompt)` (각 후보의 토큰 로그확률 **합계**). 양수이면 해당 두 후보 사이에서 Lure 상대 선호, 음수이면 Correct 상대 선호. **ΔMargin = Margin(개입 계수) − Margin(0)**. 이것은 실제 생성 응답이나 CRT 정답률이 아니다.

### 9.3 통계 검증의 의미 — Paired Bootstrap

33개 문항 각각에서 개입 전(0)과 개입 후(+7/+8)의 Margin 차이를 구한다. 그런 다음 **문항을 한 단위로 대응시켜** 복원추출 20,000회 수행하고, 평균 ΔMargin의 95% percentile bootstrap 신뢰구간을 계산한다. 이는 관찰된 평균 변화가 일부 문항에만 의존하는지, 문항 간 변동성을 고려했을 때 어느 범위에 놓이는지 탐색하는 방법이다.

| 평균 ΔMargin 및 95% CI | +7 | +8 |
|---|---|---|
| Protocol A | +0.485 [−0.235, +1.187] | +0.472 [−0.197, +1.117] |
| Protocol B | +1.342 [+0.540, +2.136] | +1.022 [+0.262, +1.793] |
| B−A | +0.857 [+0.351, +1.392] | +0.550 [+0.035, +1.077] |

B의 신뢰구간은 두 계수에서 0보다 크지만, **이 결과가 실제 정답률 증가나 일반적인 인과 기제의 입증을 뜻하지는 않는다.** 표본 33문항, 탐색적 분석, 다중 비교, 후보 길이·토큰화·프로토콜 차이의 영향을 유의한다.

### 9.4 Token-level 분석의 의미

전체 답변의 Margin은 여러 토큰에서 계산한 로그확률의 합으로 만들어진다. **첫 분기 토큰**은 Correct/Lure 후보의 토큰 ID가 처음 달라지는 위치다. **나머지 토큰**은 그 이후 각 후보 경로에서 계산한 로그확률의 차이로, 공통 prefix가 상쇄되는지 검증한 뒤 분해한다.

`전체 ΔMargin = 첫 분기 토큰 ΔMargin + 나머지 토큰 ΔMargin`

| 조건 | 첫 분기 토큰 평균 Δ | 나머지 토큰 평균 Δ | 전체 평균 Δ |
|---|---:|---:|---:|
| A +7 | +0.000000024 | +0.485425 | +0.485425 |
| A +8 | +0.253788 | +0.218576 | +0.472364 |
| B +7 | −0.219697 | +1.561707 | +1.342010 |
| B +8 | +0.017045 | +1.005423 | +1.022468 |

특히 B +7은 첫 분기에서 Lure에 불리한 변화(−0.220)가 나타나지만, 나머지 토큰 경로의 변화(+1.562)가 더 커 전체 Margin은 +1.342로 증가한다. **따라서 첫 분기 토큰만 분석하면 전체 후보 답변의 Likelihood 변화를 놓칠 수 있다.** 단, 나머지 토큰은 서로 다른 teacher-forced 후보 경로에 대한 조건부 점수이며, 특정 내부 추론 단계의 직접 증거는 아니다.

## 10. Behavioral 생성–Likelihood 프로토콜 정적 감사 및 Lure Likelihood 용어 정리

- 상세 감사 문서: [`docs/analysis/README_behavior_likelihood_protocol_audit.md`](../../docs/analysis/README_behavior_likelihood_protocol_audit.md) (commit `27ffb4d`).
- Behavioral 소스 `src/mindscopex_analysis/research.py:_binary_choice_completion`와 Protocol B 소스 `src/mindscopex_analysis/full_answer_protocols.py`, B Manifest, 실험 설명 문서를 대조함.
- **Lure Likelihood 증가의 엄밀한 의미:** 본 연구에서 주로 측정한 것은 `ΔMargin = [S(lure)-S(correct)]_intervention - [S(lure)-S(correct)]_baseline`이다. ΔMargin이 양수라도 Lure 자체 로그확률 `S(lure)`는 감소할 수 있다. 따라서 **'Lure의 절대 확률 증가'가 아닌 'Correct 대비 Lure의 상대적 선호 증가'**라고 기록한다.
- **확인된 정합성:** Protocol B는 Behavioral binary-choice 코드의 raw prompt, 원본 Correct/Lure 후보 문자열, `add_special_tokens=False` 토큰화 경로를 참조하고 CPU capture로 후보 경로를 검증하도록 구현되어 있다.
- **확인된 평가 차이:** Behavioral은 두 후보 prefix trie 내에서 `do_sample=False`, `renormalize_logits=True`의 constrained greedy generation을 사용하고 후보 완성 후 EOS를 허용한다. Protocol B는 후보별 전체 teacher-forced logprob 합계로 점수를 계산하며 EOS를 제외한다. 전체 경로 점수 우위가 greedy 선택과 반드시 일치하지 않는다.
- **미확인 사항:** 과거 Behavioral 실제 run과 B의 모델 revision·SAE·hook·실행 설정 완전 동일성은 아직 검증하지 못했다. 따라서 불일치의 원인을 greedy와 full-score 차이 하나로 확정하지 않는다.
- **결과 보존 업데이트:** 사용자 WSL 실행 로그에서 Behavioral × Likelihood 결합 결과 `results/analysis/protocol_b_behavioral_join_summary.json` 및 `protocol_b_behavioral_join_slots.csv`가 commit `31fafaf`로 GitHub `main`에 Push된 사실을 확인함.
- **다음 실험:** Behavioral 원본 실행 Manifest 및 생성 텍스트 검증 → first-branch greedy 선택과 full-answer 선호의 문항별 비교 → EOS/길이 정규화 민감도 분석 → 신규 문항 재현성 검증.
